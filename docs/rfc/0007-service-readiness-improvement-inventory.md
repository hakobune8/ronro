## 1. 目的と前提

RONROを、一回限りの評価環境から、複数の会議で継続利用できるサービスへ進める際の改善項目を列挙する。ここでいう「サービス化」は、可用性・データの扱い・利用者管理・支援体制について利用者に説明し、約束できる状態を指す。利用の単位は**個々のユーザーアカウント**、想定は**2～8名・同時4会議・1会議約2時間**とする。約2時間を超えても原則継続し、時間だけを理由に終了しない。これらは検証対象であり、性能保証値ではない。

**会議でRONROを起動するユーザーアカウント**に会議後の論点図を紐づけ、そのユーザーが記録を「預かる」。出席者への共有は**出力したPDF**に限定し、サービス上の共有リンクや受取人アカウントは初期要件から外す。退会時は紐づくサービス側の会議後データを削除する。ただし配布済みPDFはRONROから回収・削除できない。これは会議記録の継続的な管理主体を示すもので、会議内容の法的な所有権をそのユーザーだけに与える意味ではない。Pilot録音の評価担当者限定アクセスを変更しない。

製品の核は、**会議中に訂正しながら育てる論点図**である。Shared Viewは会話を妨げず現在地・決まりつつあること・未解決事項を共有し、終了後は同じCanonical Graph／Canvasを広く見る。会議後の論点図は訂正できない方針とし、会議中のHuman訂正と混同しない。従来型の文字起こし要約へ置き換えることを前提にしない。Decisionの確定、ActionのOwner／Due、Evidenceの有無は引き続き厳格に扱う。

本書は問題・根拠・確認すべき結果を記す棚卸しである。DB、キュー、認証基盤、配備方式、UI詳細、SLO値の設計は別の判断とする。優先度は初期サービスの対象（同時4会議・会議後PDF・Shared View）に合わせて再評価した。詳細は[RFC-0008](0008-account-based-service-architecture.md)と[実装設計案](../implementation/account-service-v1-design.md)に分ける。

## 2. 現在地と証拠の限界

- 2026-10-05の候補配備は、短い合成音声、Human Relation訂正、終了Drainを確認した。これはデプロイスモークであり、実会議のサービス品質やPilot開始承認ではない（[配備記録](../deployment/kubernetes-pilot-deployment.md)）。
- 現在のPilot構成は単一Pod・Recreateで、Live Session、Event Store、FIFO、Analyzer Workerがメモリ上にある。接続断への対処は進んだが、Pod喪失をまたぐ会議継続や複数会議の独立運用を保証する構成ではない（[配備構成](../deployment/kubernetes-pilot-deployment.md)）。
- T1/T2は実際の議論で課題を発見する材料であり、全会議様式の品質保証ではない。T2の短いProvider空itemにはEvidence完全性を確認できない領域がある。安全な「欠落の可能性」の表示と、実際に音声を復元できたことは別である（[実会議評価](../evaluation/real-world-discussion-evaluation.md)）。
- Semantic Canvasは合成データで5～300 Nodeの視覚検査、より大きいGraphの局所的な性能測定を実施したが、60分会議・実機3～5m・多様な話し方での受容性を保証しない（[Canvas評価](../evaluation/semantic-canvas-candidate.md)）。
- パイロットでは全員の明示的同意を条件に音声を評価用に保存し、評価担当者のみがアクセスし、会議終了7日後に削除する。本運用では生音声を保存せず、RONRO管理下のTranscript／Evidence／Graph等を会議終了から7日以内に復元不能にする設計案とする。Provider側の保持条件と、バックアップを含む復元不能性の実証は別途必要（[Pilot Guide](../pilot/ronro-live-pilot-guide.md)、[RFC-0008](0008-account-based-service-architecture.md)）。

## 3. 優先度の読み方

- **S0 — 継続提供前に判断・検証**: 未解決のまま利用者へ継続利用を約束しない項目。すべてを一度に実装するという意味ではない。
- **S1 — 提供範囲拡大前に判断・検証**: 多会議・多組織・長時間利用の前提で重要度が上がる項目。対象サービスによってS0へ繰り上がる。
- **S2 — 価値検証後に選択**: 必要性を利用者から確認して優先づける項目。

## 4. 改善項目

| ID / 暫定優先度 | 改善領域 | 現状から見える課題 | 次に判断・確認すること |
| --- | --- | --- | --- |
| SR-01 / S0 | 提供対象と品質の約束 | Pilot候補・単一会議向けの検証結果を、継続サービスの適合性と混同しやすい。 | 個々のアカウントから2～8名・同時4会議・約2時間を目安に利用し、超過しても原則継続する条件で評価する。保証値は実測後に決める。 |
| SR-02 / S0 | 会議の継続と復旧 | 現行はPod再起動や一部のProvider／ブラウザ障害で議論を中断し得る。途中再開とEvidenceの完全性は同じ問題ではない。 | 休憩など意図的な中断と再開を扱う。接続断、Provider障害、配備・Pod喪失、終了中の失敗とは区別し、各場合の継続・欠落通知を実測する。 |
| SR-03 / S0 | Canonical記録の耐久性と整合性 | Event、Graph、Human訂正、Queueのライブ状態は単一メモリに依存する。録音PVCだけではCanonical記録を復元できない。 | どの状態を会議中／終了後に残すか、再生・訂正監査・破損検出・バックアップ／復旧に必要な結果を定める。 |
| SR-04 / S0 | 利用者アカウント・認証と権限 | NetBird等の到達境界と、会議を起動し会議後データを預かるユーザーの本人確認／権限制御は別である。起動ユーザー、進行役、参加者、評価担当者が同一人物とは限らない。 | 会議と起動ユーザーアカウントの対応、`/control`、会議中のHuman訂正、Shared View、会議後の論点図の閲覧／PDF出力／削除を保護する。出席者へのPDF配布はサービス外で行い、サービス内の受取人権限は初期スコープ外。会議後の訂正権限は設けない。複数組織提供なら境界分離も必要。 |
| SR-05 / S0 | データ・プライバシー運用 | RONRO管理下の論点図・PDF・Transcript・Evidence・Graph・訂正履歴・ログは7日以内に復元不能にし、Provider側には7日要件を適用しない。 | 運営者による内部データの人手閲覧はエラー解析目的に限る。7日の起算点、退会時の鍵破棄・現用削除・バックアップ復元不能性を実証し、Provider側の実際の条件を別に確認・説明する。Pilot録音の同意・7日保持は別に維持する。 |
| SR-06 / S0 | 論点図の意味品質と安全性 | 合成ケースや一部の実会議で有用性は見えるが、Topic移動、Relation、Decision候補、display_label、長い会議の誤読率は継続評価が必要。 | 正しい現在地、訂正可能性、訂正の持続、誤った結線、否定・確度・数字の保持、Action/Decision境界を実会議・多様な会議型で評価する。 |
| SR-07 / S0 | セキュリティと障害対応 | Pilot用の境界・Secret運用はあるが、公開サービスの脅威、権限、依存関係、インシデント対応を一体として評価していない。 | 対象環境に応じた脅威・操作監査・脆弱性対応・秘密情報・不正利用・事故連絡の責任を定め、独立した安全確認を行う。 |
| SR-08 / S0 | 可観測性とサポート | 失敗をログに残す改善はあるが、利用者の「話を止めずに済むか」と運営者の「何が欠けたかを説明できるか」を継続監視する基準は未確立。 | 音声接続、STT item、可能なEvidence gap、Queue、Graph/Render、訂正、終了Drain、コストをどう観測し、誰がいつ対応するか決める。 |
| SR-09 / S0 | 配備・更新時の継続性 | Recreateによる更新は進行中Sessionに影響し得る。合成スモーク成功だけでは安全な更新運用は示せない。 | 会議中の更新可否、候補の段階的受入れ、元へ戻す判断、更新前後の記録の整合を定める。 |
| SR-10 / S0 | 同時会議・長時間・費用 | 現行の単一Analyzer WorkerとPilot容量は、2～8名・同時4会議・約2時間超の提供可能性を示さない。 | 4会議を並走させ、各会議のSTT・Analyzer・描画・費用を測る。2時間で自動終了せず、超過時の継続品質も検証する。 |
| SR-11 / S0 | Shared Viewの利用可能性 | 会議室の物理距離、表示機器、色覚・キーボード／読み上げ等、多様な利用状況での確認は限定的。 | 参加者が操作せず現在地と状態を理解できるか、実機・実会議で確認し、アクセシビリティ目標を選ぶ。 |
| SR-12 / S0 | 会議後の成果物 | Live/Finalは同じCanvasだが、出席者へ渡す会議後PDFは未実装。 | 会議後は訂正なしの論点図をPDF化する。既知の欠落可能性は該当時間帯と不確実性をPDFに明示する。配布済みPDFは退会・削除後も相手の手元から消せないことを説明する。 |
| SR-13 / S0 | 運用・オンボーディング | Pilotガイドと進行役チェックリストはあるが、日常的な問い合わせ、誤認訂正、障害告知、利用終了の担当が未定。 | 運営者・進行役・評価担当者の責任分界、導入説明、支援窓口、事故時・終了時の手順を定める。 |
| SR-14 / S2 | 外部連携と提供形態 | カレンダー、会議システム、記録出力、課金等は現時点の論点図の価値検証に必須とは限らない。 | 対象利用者が実際に必要とする連携・提供形態だけを選び、データ境界と運用負荷を評価する。 |

## 5. 横断して守る条件

サービス化のために可用性を上げても、欠けた音声を黙って「処理済み」にしない。Evidenceの欠落可能性、未完了のProvider item、Queue失敗、Graph不整合を区別して説明できること。自動Decision確定、根拠のないAction／Owner／Due、否定の反転、確度の過大表現は許容しない。Human訂正は元のAI提案と区別して監査・再生でき、古いEvidenceだけで即座に覆されないこと。Shared Viewは訂正可能な作業中の理解として表示し、参加者に常時操作を要求しない。

## 6. 上位判断：合意した方向と残る論点

| 項目 | 合意した方向 | 残る判断・検証 |
| --- | --- | --- |
| 1. 利用対象・会議時間 | 個々のアカウントで利用し、2～8名・同時4会議・約2時間を想定する。2時間を超えても原則継続する。 | 実測による品質・容量の受入れ。想定値は現時点で保証済みの上限ではない。 |
| 2. データの預かり手 | 起動ユーザーのアカウントに会議後の論点図を紐づけ、退会時にサービス側の会議データを復元不能にする。 | 鍵とバックアップを含む復元不能性の実証と参加者への説明。配布済みPDFをRONROから回収することはできない。 |
| 3. 中断・遅延・欠落 | 会議の休憩による意図的な中断・再開に対応する。遅延や記録欠落の可能性は利用者へ説明する。 | 休憩と障害を区別し、どの状態を保持するか。発生した欠落を隠さず通知する方法、継続不能時の案内、実会議で許容される影響を検証する。「可能性」の一般説明だけで、発生した障害を処理済みとはしない。 |
| 4. データへのアクセス | ユーザーは会議後の論点図を預かる。運営者によるTranscript／Evidence／Graph／訂正履歴／ログの人手閲覧はエラー解析目的に限る。RONRO管理下の会議データは会議終了から7日以内に復元不能にし、暗号化済みバックアップの物理削除は後日でもよい。Provider側には同じ期限を要求しない。 | RONRO側の7日の起算・鍵破棄・復元不能性の検証、Provider側の実条件の確認・説明、エラー解析時の承認・監査。 |
| 5. 会議後の権限 | 預かるユーザーは論点図を閲覧し、PDFに出力して出席者へ共有し、サービス側の記録を削除できる。会議後は誰も訂正しない。 | PDFが外部持ち出しであり、配布後の再共有・削除をRONROが制御できないことを利用者へ伝える。 |
| 6. 品質の受入れ | Pilot運用でのユーザー評価を中心に据える。 | 具体的な合否基準はGA時に確定する。Pilot中も自動確定・Evidence欠落・Graph破損等の安全上の問題は別途記録し、放置しない。 |
| 7. 運営責任 | 4のデータ取扱いと関連し、エラー解析時の承認・アクセス監査を設計する。 | 問い合わせ・事故連絡の担当と正式な運用責任はGA時に確定する。 |

## 7. 次の扱い

個々のアカウントによる約2時間の会議を起点に、参加者数・同時会議数とPilotでの実会議受入れ条件を詰める。横断的な設計案は[RFC-0008](0008-account-based-service-architecture.md)に、実装の参照構成と試験は[実装設計案](../implementation/account-service-v1-design.md)に分離した。本RFCだけで既存サービスをProduction-readyと判定せず、配備変更、Pilot開始、製品仕様変更も承認しない。過去の[RFC-0005](0005-meeting-minutes-generation.md)や評価記録は判断の履歴として参照し、現行方針へ無批判に昇格させない。
