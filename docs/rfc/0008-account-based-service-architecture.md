## 1. 決めること／決めないこと

RFC-0007の合意事項を、実装単位へ分解できる**候補設計**にする。個々のアカウントからRONROを起動し、会議中は訂正可能なSemantic Canvasを共有する。会議後は同じCanvasの終了時点の固定revisionを、起動ユーザーが預かる。**出席者への共有は出力したPDFのみ**であり、サービス内で受取人アカウントや閲覧リンクを発行しない。会議後は誰も訂正できない。退会時はそのアカウントに紐づくサービス側の会議データを削除する。

設計・試験の想定は**出席者2～8名、同時4会議、会議1件あたり約2時間**。2時間を超えても、時間だけを理由に自動終了せず原則継続する。これらは検証前の目標であり、検証済みSLA・人数上限・同時処理保証ではない。**7日間の保持・削除要件はRONROが管理する会議データに適用し、Provider側の保持には適用しない**。起算点は会議終了時とする設計案で、退会・明示削除はそれより優先する。Provider側の実際の条件は別途確認し、利用者へ区別して説明する。運営形態、課金、組織アカウント、外部連携は採用しない限り追加しない。既存のCanonical Node、Relation、Decision/Open Item/Actionの意味を変更しない。

### 現行からの差分

現行Pilotは1 Pod、1つの`LiveSessionManager`、実体がメモリにあるEvent StoreとFIFO、ブラウザの`controller_id`による競合防止で動く。`controller_id`は認証資格ではない。Recreate配備やPod喪失をまたぐ継続は保証しない。録音PVCはPilot評価用であり、Canonical Graphの耐久化ではない（[現行配備](../deployment/kubernetes-pilot-deployment.md)、[Live Session実装](../../prototype/live_session.py)、[HTTP経路](../../prototype/server.py)）。この構成をそのまま複数アカウントサービスとして公開しない。

## 2. 責務と正本

```text
本人確認済み起動ユーザー ── owns ── 会議Session
                                   │
音声（一時的）→ Final Evidence → 解析Job → 受理済みCanonical Event列
                                             │
                                             └→ Graph / Semantic Canvas Projection
                                                        │
                                           終了・Drain後の会議後論点図
                                                        │
                                          起動ユーザーのPDF出力
                                                        │
                                        出席者へユーザーが配布
```

| 層 | 正本／責務 | 境界 |
| --- | --- | --- |
| Identity / Access | アカウント、Session所有者、PDF出力権限、操作監査 | Graph上のNodeや発言者をアカウント所有権に転用しない。PDFの受取人認可はサービス外。 |
| Capture / STT | 現在の音声接続・Provider item、確定Transcript、未解決区間 | 本運用の生音声は永続化しない。Provider接続状態を復元できると仮定しない。 |
| Canonical | Final Evidence、Human訂正を含む受理済みEvent列 | Graphは決定的に再構成するCurrent State。Partialや表示座標は正本にしない。 |
| Service Runtime | Session状態、解析Job状態、接続世代、休憩・障害履歴、削除状態 | 議論の意味やTopic ReturnのRelationを捏造しない。 |
| Presentation | Graph＋Event Historyから導く同一CanvasのLive/Final、会議後PDF | `display_label`やCamera位置は非Canonical。権限判定を描画側だけに任せない。 |

Canonical EventとSessionの状態遷移は区別する。休憩・接続断・共有・退会は議論内容のRelationではない。会議中のHuman訂正だけが適切なCanonical Eventとなる。発話による訂正を、認証された起動ユーザー本人の操作だったと偽って記録しない。UIからの訂正は認証主体、発話からの訂正は発話Evidenceと判定経路を区別して監査する。

## 3. アカウントとアクセス

初期サービスは**個人アカウントを会議の管理主体**とし、各Sessionに1人の起動ユーザーを対応付ける。会議後記録の共同所有・譲渡は初期スコープ外。所有者と会議の発言者・進行役が同じとは限らない。本人確認は信頼できる認証基盤を使い、アプリは安定した主体IDを保持する。IDプロバイダーやログイン方式の製品選定は後続ADRとする。

| 主体 | 許されること（初期案） | 許されないこと |
| --- | --- | --- |
| 起動ユーザー | 自分の会議を開始・休憩・再開・終了。会議中の明示操作で訂正。会議後の論点図を閲覧・PDF出力・サービス側で削除。出席者へPDFを配布。 | 他人の会議を操作すること、終了後の論点図の訂正。 |
| 出席者への共有先 | 起動ユーザーから受け取ったPDFを閲覧。RONROの受取人アカウントは不要。 | RONRO上のSession制御・訂正・削除。配布済みPDFの再配布を技術的に防げるとは約束しない。 |
| 会議室のShared View | 当該Sessionの読み取り専用表示。 | Graph変更、内部Transcript/Evidence、他Session一覧へのアクセス。 |
| 評価担当者 | 同意済みPilot録音への限定アクセス。 | 本運用の全会議内容への常時閲覧。 |
| 運営者 | 内容を含まない運用指標を通常監視。内容の人手閲覧は、限定・監査されたエラー解析時のみ。 | 品質学習、営業、一般サポート等を理由にTranscript／Evidence／Graph／訂正履歴／ログを閲覧すること。 |

認可はHTTPとWebSocket接続時、各Session操作時、記録の表示・PDF出力・削除時にサーバー側で行う。ブラウザの`controller_id`、Session ID、表示URLだけを認可根拠にしない。会議室表示用の権限はSession限定・読み取り専用で失効可能にする。初期サービスはPDFをRONROから受取人へ送らず、ダウンロードした起動ユーザーが出席者へ渡す。PDFは**サービス外への持ち出し**であり、受取人の本人確認、再配布防止、配布後の失効をRONROが保証できない。アカウント退会やサービス側削除は、既に配られたPDFを消さない。この限界を出力時に分かる形で伝える。

現行`/api/live`、`/api/live/commands`、`/live`、評価用API、Fixture/開発APIは用途別に分離し、サービス提供時に意図しない公開経路を残さない。本人確認と権限の検証項目には[OWASP ASVS](https://owasp.org/projects/asvs)を参考にする。これは適合済みの主張ではない。

## 4. 保存・復旧の論理設計

初期案は、**会議ごとの永続的な処理記録**を中心に据える。特定のDB/Queue製品をこのRFCでは固定しないが、以下を満たすトランザクション可能な永続層と、必要なら後段Workerを選ぶ。単一プロセスのメモリだけを正本にしない。会議後のPDF、Transcript、Evidence、Graph、訂正履歴、内容を含むログ、派生キャッシュは、RONRO管理下では会議終了から7日以内に復元不能にする対象として追跡する。保存先が複数でも会議ID・起動ユーザーIDから対象を列挙できるようにする。

1. Final Transcript Evidenceと、それを処理すべき解析Jobを、取りこぼしのない境界で記録する。Providerの`item_id`・接続世代・ローカル音声範囲を相関し、重複Finalを二重Evidenceにしない。
2. 解析の受理済みEventとJob完了を一貫して確定する。Worker再起動や再送があっても、同一JobからCanonically accepted Eventsを二重追加しない。Provider/Analyzerへの外部呼出し自体が厳密に一度だけ行われるとは約束しない。
3. Graph、Shared View、Final Canvasは受理済みEventとEvidenceから再生成する。受理された解析出力・Prompt/Schema/Projection版を追跡し、再生時に現在のLLMを再実行しない。
4. 複数Podでも1 Sessionに同時に2人のWriterを立てないよう、Session単位の占有と世代管理を行う。接続が切れた旧世代からの遅延フレーム・遅延Finalは、新世代や別Sessionを上書きしない。
5. Backupsと復旧試験は、保存した記録が本当に再生できるかまで確認する。失われた未Final音声を、Graph再生だけで復元できるとは主張しない。

本運用では生音声を永続化しない。したがって、Pod/ブラウザ/Provider障害中に届かなかった発話は後から再構成できない場合がある。ここは`possible_evidence_gap`等の監査可能な状態として残し、利用者へ局所的に伝える。会議を続けられることと、欠落がないことを別の品質軸にする。Pilot録音の同意・7日削除・評価担当者限定アクセスは別のポリシーとして維持する（[Pilot Guide](../pilot/ronro-live-pilot-guide.md)）。Provider側の保持はRONRO側の7日削除とは別に説明する。

## 5. 会議の状態遷移

議論内容のCanonical Session状態（現行`created → active → finalizing → ended`）に、サービス側のCapture状態を重ねる。`paused`をGraphの意味上の状態として追加しない。既存Schemaへの変更要否は実装時に契約テストで確定する。

```text
created → listening → pausing → paused → resuming → listening
                 ├→ reconnecting ────────────────→ listening
                 └→ finalizing ←─────────────── paused / reconnecting
                         ↓
                 ended / ended_incomplete
```

- **休憩**: 起動ユーザーの明示操作で新たな音声取込みを止める。進行中のProvider itemを安全に収束させ、未確定ならそのまま未確定と記録する。Analyzer Jobは必要なら処理を続け、GraphとShared Viewは保持する。休憩をSession終了やTopic変更とは扱わない。
- **再開**: 同じSession・Graph・起動ユーザーで、新しい音声接続世代を開始する。旧接続からの遅延入力を受理しない。休憩時間は「発話がなかった時間」ではなく、録音・解析を意図的に止めた区間と表示できるようにする。
- **予期しない切断**: 休憩へ自動変換しない。再接続可能な状態と、欠落可能性を区別して示す。BGMや長い無発話だけでSessionを終了しない。継続不能でも既存Graphを保持し、障害を記録して再開を試みる。
- **終了**: 起動ユーザーの明示操作で取込みを止め、STT item、解析Job、Materializer、描画をDrainする。未解決音声・Jobが残る場合は`ended_incomplete`相当を保持し、`ended`と表示上も区別する。休憩中からも終了できる。
- **約2時間経過**: 時間だけでは終了状態へ遷移しない。継続中の負荷・遅延は可視化し、利用者へ必要な説明を行う。2時間超の連続運用も容量試験に含める。

操作は重複送信に安全で、Session ID、認証主体、接続世代、期待する状態／Graph revisionを確認する。会議中（休憩中を含む）のHuman訂正は許すが、`finalizing`以降の訂正を拒否する。上図は概念状態であり、HTTP応答やCanonical Schema enumの最終名を確定するものではない。

## 6. 会議後の論点図と共有

Drain後に受理されたEvent revisionを固定し、同じSemantic CanvasのZoom-outを会議後の論点図として保存・再生成可能にする。LiveとFinalで別Graphを作らない。PDFはこの固定revisionから作る会議後の論点図であり、別の要約LLMが新しいGraphを作るものではない。Nodeの状態（Candidate/Confirmed、未解決、Action）と受理済みRelationを区別する。AIのRelationをHuman確認済みの事実と見なさない。内部Transcript/EvidenceはPDFに自動同梱しない。Graph破損等で信頼できる描画ができない場合は、完成済みPDFとして出力しない。

`ended_incomplete`で欠落可能性が分かる場合も、誤って完全な記録に見せない条件でPDF出力を許す。該当する**分かっている時間帯**をPDF中に補足し、時間帯や長さが特定できないときは「範囲不明」と明記する。根拠なく欠落を特定Nodeへ結び付けない。一般的な「誤り得る」という注意と、その会議で観測された欠落可能性は別に示す。

会議後の記録は**閲覧専用**で、起動ユーザーにも出席者にも訂正機能を提供しない。起動ユーザーは終了から7日以内にサービス側の論点図を閲覧し、PDFを出力・再出力し、サービス側の記録を削除できる。出席者へ渡すのはこのPDFのみ。PDFには会議名、生成時刻、既知の欠落可能性を示す。再現性のため終了時のGraph revisionを内部では固定するが、内部IDを参加者向けに表示しない。レイアウトは大きいGraphでも全Nodeを一画面で読めると偽らない。配布済みPDFはRONROの外にあり、サービス側の7日削除・退会削除・共有取消では回収できない。出席者による再配布も技術的には防げない。

## 7. 退会・削除

会議終了時（`ended`または`ended_incomplete`としてDrainが確定した時点）をサービス側の7日保持の起算点とする設計案とする。終了できず孤立したSessionは放置せず、欠落を示した不完全終了へ遷移させて削除起算点を持たせる。会議後7日以内に、サービス側の論点図・PDF・Transcript/Evidence・受理済みEvent・Graph Projection・訂正履歴・内容を含むログと派生物を**復元不能**にし、現用コピーを削除する。評価用Pilot録音は既存の同意・7日ポリシーを別に維持する。会議や起動ユーザーを特定できる監査ログも同じ7日以内に復元不能にする。削除を証明するために7日を超えて残す記録が必要なら、会議本文・個人識別子を含まない集計値に限定できるか検証する。

アカウント退会や起動ユーザーによる明示削除は7日満了を待たずに、該当会議へのサービス側アクセスを停止し、関連データの復元不能化と現用コピーの削除を開始する。進行中会議がある場合は安全に取込みを止め、未完了状態を記録してから削除へ進む。完了確認には現用保存先、キャッシュ、レプリカ、バックアップと復号鍵を含める。結果は監査できるようにするが、監査記録に会議本文を残さない。

暗号化済みバックアップの物理削除が7日を超えても、会議ごとの復号鍵を7日以内に破棄し、バックアップからも復元不能であれば許容する、というHuman判断を採用する。ただし鍵自身のバックアップ、平文の会議タイトル・所有者対応・内容を含むログ等から復元できるなら要件未達。鍵破棄と現用データの削除、バックアップ復元試験を区別して記録する。「全コピーを7日以内に物理削除した」とは表示しない。配布済みPDFと外部Providerの保持はRONRO側の削除対象に含められない。**RONRO管理下の7日以内の復元不能化**だけを約束の対象とし、Provider側の保持と配布済みPDFはその対象外であることを明示する。法令・契約上の取扱いは対象市場に応じて別途確認する。本RFCは法的所有権を判定しない。

### 7.1 Provider側のデータ取扱い確認（2026-10-06時点）

現行のリポジトリ設定では、Realtime STTはOpenAIの`/v1/realtime?intent=transcription`、AnalyzerはOpenAIの`/v1/chat/completions`を利用する（[STT接続](../../prototype/live_stt.py)、[Analyzer接続](../../prototype/real_analyzer.py)、[Pilot設定](../../deploy/kubernetes/base/configmap.yaml)）。Providerの接続先は設定で変更可能なので、実際の配備が別Providerなら再評価する。秘密情報や実際の組織・プロジェクトのData Controls設定は本レビューで閲覧していない。

[OpenAIの公式Data Controls](https://developers.openai.com/api/docs/guides/your-data)によると、API入力は既定ではモデル学習に使われないが、明示的なデータ共有のOpt-inは別。現在の保持表では`/v1/realtime`と`/v1/chat/completions`の**不正利用監視ログは既定で最大30日**で、法令等による例外もある。両エンドポイントの通常のApplication State保持は表上`None`だが、Chat Completionsには文書記載の例外がある。したがって、**RONROのローカル保存を7日にしても、現行の既定条件だけではProvider側を含む「全データ7日」を保証できない**。

同じ公式資料では、承認を受けた組織／プロジェクトがZero Data RetentionまたはModified Abuse Monitoringを設定でき、対象となるEndpointのCustomer Contentを不正利用監視ログから除外できる。ただし適格性・承認、対象モデル、設定、例外、残るメタデータや契約条件は個別確認が必要であり、**ZDR/MAMが有効とも、Provider側が7日以内に削除されるとも仮定しない**。Provider側への7日要件は設けないが、本番で使う組織・プロジェクトの設定、データ共有Opt-in、両Endpointとモデルの適格性を確認し、適用される保持条件を利用者へ説明する。RONRO側の7日削除を「全データ7日完全削除」と案内しない。

## 8. 運用・品質・リリース

通常の監視では会議内容を読まず、Session状態、接続断、Provider item、可能なEvidence gap、Queue pending/processing/failed、Graph/Render revision、Drain、PDF生成・削除Job、費用等の最小限の指標を使う。内容に触れるエラー解析は、**解析担当者とは別のプライバシー／セキュリティ承認者**が、障害Ticket・対象Session・閲覧する項目・理由・有効期限を確認して許可する設計とする。許可と実際の閲覧を監査し、期限後は失効する。担当者個人の指名と緊急時の代行手続はGA前に確定する。問い合わせ担当者が自動的に内部データの閲覧権限を持つわけではない。事故の検知・通知とデータ閲覧の権限は別に設計する。

2～8名の約2時間の会議を、通常の発話、休憩、雑音、複数Topic、Relation訂正、長い無発話、切断・復帰、終了Drainを含めて検証する。さらに4会議同時実行と、2時間を超えて継続した場合のSTT/Analyzer待ち、投影遅延、Graph規模、費用を測る。300/600/1000 Nodeの合成Projection測定は有用だが、2時間実会議の体験保証へ直接読み替えない（[Canvas評価](../evaluation/semantic-canvas-candidate.md)）。Shared Viewは会議室の実機・実距離で評価し、アクセシビリティの目標は[WCAG 2.2](https://www.w3.org/TR/WCAG22/)等を参考に選ぶ。適合済みとは主張しない。

更新時は新規Sessionの受付と進行中Sessionの終了・移管を区別する。現行`Recreate`による進行中会議の停止を、サービスの通常更新手順として前提にしない。障害時もSessionの正本を再読込できる設計を先に検証する。具体的なPod/Queue/DB製品、ルーティング、Blue/Green等は後続の配備設計で比較する（[Kubernetes Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)）。

### 受入れゲート（具体的な合否値・運用責任者はGA時に確定）

1. **ユーザー評価**: Pilot参加者が「議論を止めず、現在地・決まりつつあること・残ることを共有できる」と評価する。進行役の負担と休憩・再開の体験も確認する。
2. **安全**: 自動Decision確定、根拠のないAction/Owner/Due、Graph破損、Human訂正の消失、静かなEvidence欠落は許容しない。誤ったRelation等は訂正でき、訂正後に古いEvidenceだけで復活しない。
3. **継続**: 2～8名・同時4会議・約2時間超のSession、休憩・再開、接続断・復帰、Worker/Pod障害、更新中の挙動を試験し、継続可能範囲と既知の欠落を明示する。
4. **アクセスと削除**: 他アカウントによる越権、会議後の訂正、削除後のサービス側再表示を防ぐ。PDFの外部持ち出し例外を説明し、サービス側の7日以内の復元不能化をバックアップ復元試験まで実証する。Provider側の実際の保持条件は別に確認・説明する。
5. **運用**: Content-freeの指標から問題を発見し、必要時だけ限定的なエラー解析へ移れる。障害告知と利用者向け説明が矛盾しない。

## 9. RFC-0007改善項目との対応

以下は設計上の対応であり、実装・試験完了を意味しない。状態・データ境界・API・失敗時の扱い・受入れ試験は[実装設計案](../implementation/account-service-v1-design.md)で具体化する。

| SR | 本RFCでの設計境界 |
| --- | --- |
| 01 / 10 | 個人アカウント、2～8名・同時4会議・約2時間超も継続する想定、容量試験。 |
| 02 / 03 / 09 | 休憩と障害の別状態、永続的な処理記録、再開・更新時の正本復元。 |
| 04 / 05 / 07 | 起動ユーザーの所有、PDF出力権限、限定された運営者閲覧と承認、7日削除、Provider側保持の確認。 |
| 06 / 11 / 12 | Canonical保全、同一CanvasのLive/Final、会議後PDFのみの共有、実会議・実機評価。 |
| 08 / 13 | 内容を読まない通常監視、エラー解析時の権限、問い合わせ・事故対応。 |
| 14 | 連携・課金は価値検証後の選択。初期サービスの必須依存にしない。 |

## 10. Human Reviewで決まった方向と残る検証

| 論点 | 決まった方向 | 実装・GA前に残る確認 |
| --- | --- | --- |
| 出席者への共有 | 起動ユーザーが出力したPDFのみ。受取人アカウント、サービス内の共有リンクは初期案に含めない。 | 配布済みPDFの回収・失効・再配布制御はできない旨を出力時に伝える。PDFの誤配布対策と閲覧性を検証する。 |
| 利用規模と時間 | 2～8名、同時4会議、約2時間を設計・試験の想定とする。2時間超も原則継続。 | 実測前の保証値とはしない。並行実行、長時間、障害復帰、費用を検証して提供条件を決める。 |
| 保存と削除 | RONRO管理下の論点図・PDF・Transcript／Evidence／Graph・訂正履歴・ログを会議終了から7日以内に復元不能にする。暗号化済みバックアップは、鍵破棄後に物理削除が遅れても可。退会・明示削除は前倒し。Provider側には7日要件を適用しない。PDF配布はサービス外への持ち出し。 | 鍵を含むバックアップ、平文メタデータ、キャッシュ、ログを含めて復元不能性を実証する。Provider側の適用条件は別に確認し、利用者向けの保存・削除説明を分ける。 |
| 不完全終了の共有 | `ended_incomplete`でも、観測した欠落可能性のある時間帯を補足したPDFを出力可能とする。特定不能なら範囲不明と示す。 | 警告の配置、時刻精度、欠落の根拠とPDF生成の安全性を確認する。一般的な注意書きとは分ける。 |
| 内容への人手アクセスとProvider | エラー解析時に限り、解析担当とは別のプライバシー／セキュリティ承認者が対象・理由・期限を許可し、閲覧を監査する。現行Endpointの公式Data Controlsは§7.1で確認した。 | 実際の承認者・代行、監査ログの保持と削除、OpenAI組織／プロジェクトの実設定・モデル適格性・例外条件を確認する。 |
| 品質・運営 | Pilotユーザー評価を中心に、安全上の問題は独立して扱う。 | 数値を含む合否基準、問い合わせ・事故連絡の担当はGA時に確定する。ただし確定前のPilotでも安全事象を放置しない。 |

権限・RONRO側の削除・可用性を実証する前に「保証済み」とは表現しない。Provider側の保持条件は実際の契約・設定で確認し、RONRO側の7日要件と混同しない。設計の採用後も、移行手順・保存方式・認証製品・運用責任は個別の実装計画で検証する。本RFCは既存Pilot配備や参加者向け案内を変更しない。
