# Golden Annotation v2

Status: Proposed evaluation baseline

Golden Version: `golden-v2`

Evaluation Version: `analyzer-eval-v2`

## Purpose

Golden v2 is a versioned semantic evaluation baseline for the five Recorded
Analyzer Scenarios and 38 Utterances. It is not a replacement for the v1
annotation and it is not a model-specific expected-output file.

The v2 Golden describes the Discussion structure that is useful for a shared
Discussion Map. Equivalent Japanese labels are accepted when they preserve the
same meaning, polarity, scope, and Node type.

The source JSON files are under:

`evaluation/golden/v2/`

## Versioning and historical integrity

- v1 remains under `evaluation/real-analyzer/**/annotations.json`.
- Run #2/#3/#4 Raw, Parsed, Final Graph, `metrics.json`, and review documents
  are unchanged.
- Re-score outputs are Derived Evaluation artifacts under
  `evaluation/rescored/golden-v2/`.
- A future change to Golden v2 must create another Golden version rather than
  silently changing this one.

## Strong / Weak / Not Decision

### Strong Candidate Decision

A Strong Candidate Decision requires a concrete choice, scope boundary,
adoption, or rejection and explicit commitment/selection language. Examples
include:

- `〜で進めましょう`
- `〜にしましょう`
- `〜を採用します`
- `〜から外しましょう`
- `〜を第一候補にしましょう`

The four v2 Strong candidates are:

| Utterance | Scenario | Meaning |
| --- | --- | --- |
| `real-a-u005` | MVP企画 | Smartphone UI is excluded from MVP |
| `real-b-u006` | Architecture | Materialization is deterministic and the LLM is outside the materializer |
| `real-d-u006` | 意見対立 | Usage-based pricing is the first MVP candidate |
| `real-e-u001` | Topic Return | Shared-display Discussion Map is the MVP center |

These remain Candidate Decisions, not Confirmed Decisions. Only a Human
Command can confirm them.

### Weak Decision Signal

A Weak Signal contains a useful direction, preference, or scope signal but its
commitment is too weak to require a `decision` Node in the MVP Map. Examples:

- `〜の方がいいと思います`
- `〜でもいいかもしれません`
- `〜がよさそうです`
- `〜という案もあります`

The most important weak signal is `real-e-u005`: it says `スマホUIは対象外で
よさそうです`, which identifies a scope direction but does not explicitly
commit the group to it. Run #4's Option representation is acceptable.

Weak Signals are measured separately and are not counted as missed Strong
Decisions.

### Not Decision

The following are not new Decision Candidates:

- preference without selection;
- question or unresolved item;
- brainstorming option;
- general framing or explanation without a concrete selection;
- agreement such as `そうですね`, `賛成です`, `了解です`, or `それでいきま
  しょう` when the current utterance does not state the proposal;
- any Human Confirmation event generated by the Analyzer.

## Evaluation strictness

### Strict checks

The following are evaluated exactly or deterministically:

- Event category and allowed vocabulary;
- Strong Decision safety;
- Action safety;
- Owner and Due Date existence;
- Existing Topic ID for Topic Return;
- Topic Return accuracy;
- duplicate Topic acceptance;
- Relation Matrix validity;
- Human Confirmation boundary.

### Semantic checks

The following accept semantic equivalents rather than exact strings:

- Topic labels;
- Idea labels;
- Option labels;
- Concern labels;
- Open Item labels.

For example, `料金体系` and `料金モデル` can match when their context and
Node type are equivalent. A semantic match must not erase polarity or scope:
`対象外` must not become `対象`, and a preference must not become a Decision.

## Policy for product evaluation

Only Strong Candidate Decisions are required to appear as `decision` Nodes in
the primary Map evaluation. A Weak Signal represented as an Option, Idea, or
Open Item is acceptable and is not a False Negative against Strong Decision
Recall.

False Strong Decision is higher severity than a missed Strong Decision:

- False Strong Decision: High severity;
- Missed Strong Decision: Medium severity;
- Weak Signal represented as Option: acceptable;
- Weak Signal represented as Strong Decision: error.

## Other annotation dimensions

The v2 files retain the existing Topic, important Node, Action, Topic Return,
and no-op coverage, while allowing semantic label equivalence. Action policy is
unchanged: explicit execution intent only; Owner and Due Date are null unless
explicitly present in Evidence.

No-op utterances remain an important product signal because the Map must not
become a transcript visualization.

## Known calibration consequence

Applying the same Strong rule to `real-b-u006` and `real-e-u001` makes two
previously omitted v1 expectations explicit. Run #4 is intentionally allowed
to reveal those misses: evaluation calibration must not be changed solely to
make the latest Prompt score better.
