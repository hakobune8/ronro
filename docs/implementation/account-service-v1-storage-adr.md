# Account Service v1 — Content Store ADR (P1)

Status: Content-store choice accepted for implementation; Key Registry selection/deployment and 7-day irrecoverability remain unverified. 既存OpenBaoを検証候補とするHuman判断を記録した。

## Decision

Use PostgreSQL as the transactional content database for Account Service v1. Keep it separate from the current single-Session Pilot runtime. The additive migrations currently extend through [`0015_withdrawal_receipt.sql`](../../migrations/0015_withdrawal_receipt.sql); Service routes are not enabled by applying them.

The migration runner takes a PostgreSQL transaction-scoped advisory lock and records the filename and SHA-256 checksum in `service_schema_migration`. Repeated application of the same file is a no-op; an edited applied migration is rejected. New schema revisions must use a new numbered file rather than rewriting an applied one. Provisioning and the production migration principal remain external to this adapter.

The service writes each accepted Final together with its Analyzer Job in one transaction. A Worker claims a Job with a lease and PostgreSQL row locking; acceptance of output, ordered Canonical Events, Graph revision/checkpoint, and Job completion is another Session-serialized transaction. A stale claim or Graph revision cannot append Events. `session_ended` and frozen final revision are accepted together; later Worker output cannot mutate the meeting. Events remain the replay source of truth; a checkpoint is a rebuildable cache.

New Service routes should use `open_session`, which accepts owner binding, Session row, and the first Canonical `session_created` Event in one content-DB transaction. The older `create_session` helper remains for synthetic contract setup and must not be used as a public route. An unsuccessful or uncertain content-DB transaction can leave a key-only orphan; it must be reconciled after the DB outcome is known, not destroyed immediately on exception.

`open_session` serializes admission across replicas using a transaction-scoped PostgreSQL advisory lock. It counts `open` Service Sessions before creating the Session key, enforces a configurable positive limit (candidate default 4), and raises `capacity_unavailable` without creating a key when full. An ended Session no longer consumes a slot. The global lock deliberately covers external key creation for atomic capacity decisions; its latency and crash behavior still require load and Key Registry testing. This is a safety gate, not evidence that four two-hour meetings meet the performance target.

The Store exposes attempt-fenced lease renewal for Analyzer calls longer than the initial lease. `ServiceAnalyzerWorker` heartbeats while Analyzer inference is in flight, stops the heartbeat before committing, and refuses acceptance if ownership renewal could not be verified. A stale attempt cannot renew after another Worker reclaims the Job. This prevents normal slow calls from causing duplicate Provider calls; network partitions may still lead to repeated calls, but attempt fencing prevents duplicate accepted Events.

Global Job claim prefers the least-recently-claimed Session while the existing per-Session predecessor rule keeps Utterances ordered. This is an initial fairness mechanism, not proof that four two-hour meetings meet latency or cost targets. `last_claim_at` is plaintext operational metadata and is part of the seven-day deletion/privacy review.

For Realtime intake, `ServiceFinalIngestor` accepts the existing gateway's correlated Final event shape and uses the existing v2 normalizer without retaining raw Provider payloads or audio. `accept_provider_final` requires the audio connection ID and Provider item ID. It derives a Session-keyed opaque item identity, assigns the Final sequence while holding the Session row lock, and inserts Evidence plus Job atomically. An identical retry returns the accepted identifiers (including after Drain); a conflicting retry fails. Reused Provider item IDs on different connections remain distinct. The `intake_closed` fence is set atomically with `session_finalizing`, so a later Analyzer Event cannot accidentally reopen STT intake. The authenticated Service WSS gateway still needs to call this adapter. Unknown item identity or unknown audio coverage fails closed until P3's durable gap ledger can represent it; it is not silently guessed from transcript text.

Meeting content columns use per-Session AES-256-GCM with authenticated context consisting of Session, record kind, and record identity. This includes owner identity, Evidence/Utterance text, Canonical Event payload, Analyzer output, and checkpoint. A Provider item ID is stored as a keyed digest, not raw text. Keys are never stored in the content database. Session IDs and processing state remain plaintext operational metadata; their re-identification risk must be reviewed with logs and backups before release.

Accepted non-Canonical `display_label` hints are encrypted on the completed Analyzer Job, independently of Canonical Events. Acceptance validates the Node/event/content identity and is in the same transaction as the Job and Events. Replay reconstructs these hints in Job/utterance order; a missing or invalid hint falls back to Canonical Node text. Checkpoints remain Canonical-only, so losing a checkpoint does not lose accepted presentation hints. This preserves the Pilot separation between semantic truth and replaceable Shared View representation.

The production API must generate opaque Session/Event/Evidence/Job identifiers; it must not accept participant names or free text as indexed identifiers. The database migration is applied by a separate privileged identity. The live application identity should have only the DML permissions needed for its Session-scoped operations, not routine DDL access.

The P2 storage boundary checks a verified internal owner ID against the encrypted Session owner within a transaction. A different owner and a nonexistent Session return the same `session_not_found` result. `0004_view_credentials.sql` adds only hashed, short-lived, revocable, Session-scoped live-Canvas credentials; bearer material is returned once and never stored in plaintext. Credential lookup also checks the live Session state, so ending the meeting revokes display access. These methods are **not** an OIDC login, HTTP authorization middleware, WSS revocation mechanism, or permission for Commands/Evidence/PDF. They remain disconnected from public routes until issuer verification, account lifecycle, CSRF/Origin, and route-specific authorization are implemented and tested.

`0009_service_identity.sql` adds account identity and Web Session records outside the meeting-content tables. A separately supplied 32-byte identity key derives distinct HMAC and AEAD keys; the DB stores only a keyed `issuer + subject` digest, encrypted short-lived state/nonce/PKCE attempt, and Web Session/CSRF digests. OIDC attempt consumption is an atomic delete before code exchange, including concurrent callback rejection. User mapping accepts only the verifier's `VerifiedOidcIdentity`, and the internal owner gate composes Session-bound browser authentication with the existing encrypted owner check. Expired auth records can be purged independently of meeting data. The loopback-only candidate now tests HTTP/WSS authorization and account withdrawal, but this is synthetic PostgreSQL evidence, **not** proof of durable identity-key operations, live ZITADEL login, deployed route enforcement, or actual key destruction.

`0010_oidc_browser_binding.sql` adds a keyed digest of the initiating browser's short-lived Host-only login cookie to each new authorization attempt. A callback from another browser cannot consume the state, while two tabs sharing the legitimate browser cookie may complete separate attempts. Legacy/unbound attempts are rejected until they expire. CSRF material is deterministically derived from the authenticated opaque Web Session cookie and the separately held identity key, so another same-origin tab can retrieve the same token without persisting plaintext. The local-only authentication HTTP candidate exercises this flow with synthetic signed ID Tokens; it is not mounted on Pilot or deployed and cannot establish real ZITADEL interoperability.

The P3 storage foundation keeps Capture state and generation outside Canonical Events. Owner requests for start/pause/resume use a per-Session operation key and expected version; gateway acknowledgements are separate and must come from a trusted internal path. `resuming` does not claim that audio is already being accepted. A pause interval is recorded as intentional `paused`, not an Evidence gap; the post-resume or disconnected interval is recorded as `capture_unavailable`, meaning a **possible** gap, not confirmed lost speech. The old generation cannot acknowledge a newly resumed connection. `session_finalizing` and `session_ended` fence Capture updates in the same content transaction as the Canonical Event. This foundation is not yet a complete WSS/frame/Provider recovery loop and must not be surfaced as such.

The frame-receipt ledger stores only the current generation's accepted sequence high-water mark, sample count, audio-end time, and per-Session keyed digests of the connection and last frame. It does **not** persist PCM. The trusted gateway must record a frame before attempting Provider append; this proves receipt by RONRO, not Provider acceptance or Evidence completion. Repeated last frames with identical PCM are idempotent; conflicting repeats are rejected. Sequence gaps, unexpected connection replacement, or audio-clock discontinuities fence the generation and leave a `capture_unavailable` interval. A connected socket alone no longer closes that interval: the first durably accepted PCM frame does. Missing sequence bounds are stored when known; an unknown audio duration must remain unknown. This is a metadata foundation only; the live gateway and Provider item ledger have not yet been connected, and per-frame database-write performance remains unverified.

The P3 Provider-item ledger records `input_audio_buffer.committed` identity and predecessor, local generation/frame/audio range, and item-specific transcription completion. Only keyed digests of Provider connection/item/event IDs and transcript content are stored; transcript text is accepted into encrypted Evidence only after the completed item and Final text match. Completion-before-commit remains unmatched until correlated. An older Provider item must be accepted before its later item can become numbered Evidence when `previous_item_id` is supplied. An unresolved, empty, or unknown-coverage item prevents a falsely complete Drain; it may only end as incomplete until a later policy explicitly distinguishes benign silence from possible Evidence loss. A tracked item may finish after intake closes but before the final revision freezes. This matches the [official Realtime transcription guidance](https://developers.openai.com/api/docs/guides/realtime-transcription#handle-transcript-events), which does not guarantee completion ordering across turns and directs correlation by `item_id`. These tests use synthetic Provider events only. The gateway still must bind actual Provider append/commit to trusted local frame ranges, handle reconnect/generation transitions, and verify model/VAD compatibility before Service exposure. A local frame receipt alone is **not** proof that the Provider received or transcribed those samples.

The P5 retention boundary stamps `ended_at` and `expires_at = ended_at + 7 days` in the same accepted `session_ended` transaction. Owner-scoped deadline reads and content-free counters expose missing or overdue deadlines; `created_at` is not used to guess an old meeting's end. A deletion Job now fences access 15 minutes before expiry, or immediately after an owner delete/account withdrawal request; the synthetic key registry test proves DB cascade after the key becomes unavailable. The real OpenBao adapter deliberately refuses to claim verified destruction. Backup restoration, real key deletion, private PDF/object deletion, and alert delivery remain required before any user-facing seven-day retention promise.

The P5 PDF boundary reads only an owner-authorized ended Session at its fixed final revision. It validates Domain schema and a fresh Event replay before rendering. Its first-page map uses the same deterministic Semantic Canvas coordinates as Live, with semantic zoom for outcomes and their local backbone; subsequent sections distinguish confirmed/candidate Decisions, active Open Items, Actions, explicit owner/due, and full Canonical Node text. The print renderer makes no LLM call, reads no raw transcript into the PDF, and marks `ended_incomplete` or captured unavailability as a possible gap without confusing deliberate pause. Synthetic A4 page rendering is visual-QA evidence for the renderer only. The loopback-only Service HTTP candidate now exposes an owner-cookie-only, no-store PDF download at the frozen revision; display bearers and foreign users cannot access it. It still has no public Service route, private object-store lifecycle, or recipient delivery; those remain P2/P5 gates.

The `SessionKeyRegistry` protocol is a separate boundary. `InMemoryTestKeyRegistry` exists only for synthetic tests and is rejected unless the PostgreSQL adapter is explicitly placed in test mode. Before any real meeting uses this adapter, implement a durable, separately operated Key Registry and prove both key availability under node loss and key destruction within seven days including its own copies. A content-DB backup alone is neither recovery proof nor deletion proof.

既存OpenBaoをKey Registryの検証候補とする。これは採用確定や本番鍵作成の承認ではない。既存インフラのOpenBao運用資料は現在の配置を単一ノードPoC（`replicas: 1`）と明記し、暗号化Raft snapshotを復旧手段とする。これはRONROの可用性や7日削除を満たす証拠ではない。OpenBao [KV v2](https://openbao.org/docs/secrets/kv/kv-v2/)の通常削除は復元可能で、version destroy/metadata deleteと区別が必要である。さらに[Raft snapshot restore](https://openbao.org/docs/next/commands/operator/raft/)で削除前の鍵が復元され得るため、**現行snapshotの保管期限・全コピー・復号可能性を照合できるまで7日以内の復元不能化を宣言しない**。Transit/KVの採用、RONRO専用の最小権限認証・path/mount、会議別鍵の全コピー、破棄手順、OpenBao自身のbackupとnode loss復旧、7日後の復元否定を分離して検証する。この判断前に実会議データを新Storeへ投入しない。

Human判断により、現段階のスコープはRONRO側の接続実装までとし、既存OpenBaoのインフラ変更は含めない。`prototype/service_openbao_keys.py`は専用KV v2 mount `ronro-session-keys`へのHTTPS/CA検証、短命workload token取得、UUID path固定、CAS=0での会議別DEK作成と読出しだけを合成HTTPで検証する。実行時接続は`OpenBaoKvSessionKeyRegistry.from_environment()`で`RONRO_SERVICE_OPENBAO_URL`（HTTPS origin）、`RONRO_SERVICE_OPENBAO_CA_FILE`（絶対パス）、`RONRO_SERVICE_OPENBAO_TOKEN_FILE`（絶対パス）を束ねる。token値を環境変数へ置かず、要求ごとにマウント済みファイルを読み直してcredential rotationに追従する。設定・token欠落時はfail-closedとし、Proxy環境変数・redirectは利用しない。この設定経路とtoken rotationも合成HTTPでのみ試験した。既存証明書用`kv` mountへは書かない。専用mount/policy/authは未作成であり、実OpenBao接続・単一ノード障害復旧・snapshot期限の試験も未実施。`delete_key`は意図的に`key_deletion_unverified`で失敗し、KV soft-deleteを7日破棄と誤認させない。このアダプタを実会議Storeへ接続する前に、専用mount・workload identity・backup/restore・鍵破棄の運用承認が必要である。

## Current evidence and remaining work

- Local PostgreSQL integration uses synthetic data only: encrypted rows, reopen/replay, duplicate Final, atomic rollback, Session isolation, stale revision, failed-Job retry, incomplete end, and checkpoint rebuild. A content-DB dump restored into a separate database replayed the same Events while the test key was available; after deleting that key, the restored content was unreadable. This does **not** prove a durable Key Registry or the seven-day production deadline.
- A one-Job `ServiceAnalyzerWorker` now exercises the existing Analyzer interface outside the DB transaction, validates/stages Candidate Events, and atomically accepts Events plus non-Canonical presentation hints. Synthetic SQLite and PostgreSQL tests demonstrate this boundary and process reopening. Handled failures persist only a content-free error code and require an explicit retry; a process crash leaves the lease claimable after expiry. It is not a continuously running, production-supervised Worker. The current Pilot remains on its existing path.
- The separate loopback candidate wires authenticated HTTP/WSS, Provider-item intake, PDF rendering, and fail-closed deletion to the Store using synthetic data. It is not exposed by the Pilot entrypoint or a public Service route.
- P1 still requires a **real** durable Key Registry integration (the OpenBao adapter is synthetic-only and deliberately cannot delete keys), public authenticated routing, supervised Worker deployment, production migration credentials/rollback procedure, backup restore with durable keys, and performance testing. The local version/checksum ledger is not a deployment or rollback procedure. P2–P6 remain separate gates.
- In a two-system create (Key Registry then content DB), an uncertain DB commit must not trigger immediate key deletion. Orphan-key reconciliation is required before service exposure.
